Beside page 9 · where a body runs

Houses

A house is the container image an agent's body runs in. Loom provides the core of it; one file in the agent's own repository, the Housefile, adds the rest.

Any worker builds and runs any agent's house. Nothing is set up on a machine for an agent.

What it is

A house, a worker and a Housefile

A container for a body

jobstartscontainerfromhouse image

A body is one run of an agent on a machine. It runs in a container, and the image that container is made from is the agent's house. The house holds what the agent works with: its harnesses (a harness is the program a model runs in, such as Claude Code or Codex), its tools, and its own repository.

One worker, any agent

  • A container engine
  • git
  • The loom worker, signed in to loom

A worker runs any agent's house. Nothing is installed or configured on the machine for an agent: once a machine has a worker that loom knows, any agent allowed to run there can be sent to it, and its house is built there the first time it is needed. What a machine does hold is model sign-ins, which belong to accounts and not to agents.

A core house, and the agent's furniture

  • loomprovides the core house
  • the Housefileadds the agent's own things
  • no Housefilethe core house and the repository

Loom provides a core house: the system, the basic tools and the harnesses, laid out the same for every agent. An agent's own repository adds to it with one file, called a Housefile, which is an ordinary container build file. An agent that names no Housefile lives in the core house with its repository copied in.

Where it is named

An agent's run settings

An agent's run settings name its house

  • Repository. The address of the git repository that holds the Housefile. It must be an https:// address.

    set by the agent's owners

  • Housefile. The file's path inside the repository, for example Housefile or house/Housefile. Left empty, the agent has no Housefile: it runs in the core house with its repository copied in, and a card that proposes this says so in words.

    set by the agent's owners · may be empty

  • Branch. The branch to build. Each job builds the commit that branch is at when the job starts.

    set by the agent's owners

  • Repository secret. For a private repository: the stored secret that fetches it. Left empty for a public one.

    a stored secret, named here

  • Startup secrets. Stored secrets a body is handed when it starts, each under an alias. The alias is the name of the environment variable the body finds it in.

    a stored secret and an alias, each

Who decides

  • An agent's owners set its run settings. An agent can propose a change to its own; a person allows it before it takes effect.

    People and projects · Tools for agents

  • A secret named here is still a stored secret: who may use it, and whether a person is asked first, is decided by its own rule.

    Secrets

  • A job keeps the repository, Housefile and branch its agent had when the job was admitted. Changing the settings does not change a job already waiting.

    Machines and jobs
The Housefile

What a house says about itself

An ordinary container build file that starts from the core house. Where things are inside a house is the same in every house, so the image says only two things with labels, and the core says both. Loom reads labels, and not a file inside the image, because an image's labels can be read without starting anything from it.

# The house of the agent Fern: the image a body of hers runs in.
# A loom worker builds it from this repository at one commit, on the core house loom provides.
# The worker hands every build the core house's image under this name.
ARG LOOM_CORE
FROM ${LOOM_CORE}

# Furniture: what this agent wants beyond the core. The core already has the system, git, Node,
# Claude Code and Codex, the home at /home/agent, a body file for each harness, and both labels.
RUN apt-get update && apt-get install -y --no-install-recommends ffmpeg \
 && rm -rf /var/lib/apt/lists/* \
 && git config --global user.name "Fern"

# This repository's own files, at the place every house keeps its repository. A body starts there.
COPY . /home/agent/repo

A complete Housefile. Everything loom needs of a house comes with the core, the body files among them. A body file is one line, such as {"command": "/usr/local/bin/claude", "cwd": "/home/agent/repo", "reach": "all"}: the harness program in the image, the directory it starts in, and reach, which is loom for loom's own tools only or all for the harness's own tools as well (files, a shell, the web). A Housefile may put its own body file over the core's. One that does not start from the core still works, when its image has the labels and the layout below by itself.

What the image must say

  • loom.house is the version of this agreement between a house and loom, and of the layout beside it. It is 2. An image that says 1 is refused.

    a label

  • loom.house.harnesses names the harnesses the house serves, with a space between: claude, codex, agy. It is the one thing houses differ in that loom must know before it starts a body.

    a label

  • An environment. A body runs with the image's ENV, and as the image's USER. Loom sets two variables of its own: the home, and the body's scratch directory. The image's WORKDIR is not read.

    ENV · USER

Where things are in every house

  • The home is /home/agent. No path in a house is named for its agent: who lives there is the repository it was built from. Loom sets HOME to it when a body starts.

    /home/agent

  • The agent's repository is at /home/agent/repo. Every body starts in that directory.

    /home/agent/repo

  • Node is at /usr/local/bin/node, Node 22 or later. Loom's body program is run with it. The core house has it.

    /usr/local/bin/node

  • A harness's body file is at /etc/loom/body/<harness>.json, one for each harness the house serves.

    /etc/loom/body

  • An account's sign-in appears at /run/loom/login/<harness> when a body starts. The core house points Claude Code and Codex there.

    /run/loom/login

  • The user. The core house names none, so a body in it runs as the container's root. On a machine whose engine runs without root, that is the worker's own user outside the container, the one that can write the mounted sign-in.

    root inside the container

  • A repository must not assume its own name in a path, a home other than $HOME, or a user of some name. A house that wants an older path makes a link to the fixed one.

    the same on every machine

What the image must not hold

  • A copy of loom. Loom mounts its own body program into every container at /opt/loom, so the image must keep nothing there.

    nothing at /opt/loom

  • A declared volume. Loom checks that a container has exactly the storage it asked for, and an image that declares a VOLUME is refused.

    no VOLUME

  • A credential. A sign-in, a token or a key in an image is in every copy of that image. A body gets its model sign-in and its secrets when it starts, from outside the image.

    nothing secret

  • Anything that is not in the repository, in the core house or at a public address. The build is given the repository's files and the core house's name, and nothing else: no secret, no file of the machine.

    builds from the repository and the core
How it works

When a job needs a house

1 · Fetch

  1. https onlyno ssh, no path, no plain http
  2. no user settingsnone of the machine user's git configuration or credentials
  3. one committhe branch as it is now

The worker fetches the branch with the machine's git, into a copy of the repository it keeps for itself. Git is used to store and hand back the repository's objects, and nothing more: it runs with none of the machine user's settings, takes no address but an https one, and is not asked to check out, inspect or run anything. The reason is that whoever may set an agent's house chooses the address, and must not thereby borrow the machine user's access or have a program started. A repository secret is given to that one fetch and kept nowhere.

2 · The files of the commit

  1. goes inevery file, byte for byte; links as links
  2. left outsubmodules
  3. refusedover 100 MiB a file, 1 GiB in all, 50,000 files

The worker writes the build's input itself: every file of the commit, byte for byte, with whether it is executable, and every symbolic link as a link. Nothing in the repository changes what goes in: files that tell git to leave things out, substitute text or convert line endings are ordinary files here. A submodule is left out. A commit past the limits, or with a file name that could land outside the build (an absolute name, a name with .. in it, one name twice), fails the job before anything is sent.

3 · Build

core housethenthe Housefilebuildsimage

The machine's container engine builds the Housefile, on the core house. The worker builds the core house first when the machine does not have it: from a definition that comes with loom, never from an image someone published, so a machine whose worker was installed a moment ago needs nothing else. The core's build counts toward the same limit. A build has 30 minutes unless the machine's configuration says otherwise, and 60 at most; a job still waiting then fails, saying the build ran out of time. While a house builds, the worker goes on telling loom the job is alive, so a long build does not lose the job. Before there was a core house, a first build of a house with the same tools from a bare base image took about ten minutes on a small machine and made an image of about 1.5 GB; the core house itself has not yet been built on a machine.

4 · Found again

  • the same committhe image is reused
  • a new commitbuilt, reusing unchanged steps
  • a new weekbuilt again, once

An image is named for its repository, its Housefile, its commit and the core house it was built on. The next job at the same commit finds the image and starts at once. A new commit is built, and the engine reuses the steps that did not change. The core house is built again once in each new week, which keeps its system current, and when a new loom changes its definition; each house is then built again on its next job. A job that already has its image is never interrupted for this. No image holds any of loom itself.

At run time

What is not in the image

What a body is given when it starts

  • Loom's body program. The program that takes the job, starts the harness and reports back. It comes from the worker's own installation, read-only, so it is always the one that matches the loom that is running.

    mounted at /opt/loom

  • Its account's sign-in. A model sign-in is a directory of files that the harness's program rewrites when it renews, so it cannot be in an image. The machine's configuration names one directory for each account and harness, and a body gets the one for its job's account and no other, at /run/loom/login/<harness> in every house on every machine. It is the same directory for every body on that account, never a copy: a renewal changes the sign-in, so copies would cancel each other. Loom does not read, clean or write anything in it.

    mounted at /run/loom/login

  • Its agent's own directories. The machine's configuration can give an agent directories of the machine, read-only unless it says otherwise: a little state kept between bodies, say. Each lands under the home, at the path the configuration gives, and never on the repository. A body gets its own agent's and never another agent's.

    from the machine's configuration

  • Its startup secrets. Each is in the environment of the harness under its alias. They are handed over when the body starts, not before, and are in no image.

    Secrets

  • Its job. The work, and a credential of its own that is good for this one job.

    Signing in

What it is not given

  • Anything else of the machine. No other directory, no other account's sign-in, none of the worker's environment, and not the engine itself unless the agent is allowed nested containers and the machine has opted in.

    nothing by default

  • A body allowed nested containers holds the machine's container engine, and through it everything that engine's user can reach, every account's sign-in included. It is allowed only where both the agent's settings and the machine say so.

    a stated exception
On one machine

Several jobs at once, and the disk

Slots

  • slots4 unless the machine says otherwise
  • at most16

A worker runs several jobs side by side, each in a slot. A house being built takes one slot, so another agent's job, whose house is already built, starts in a free one. Two jobs that want the same new image wait for one build. Loom keeps no count of a machine's jobs: a worker asks for a job only when it has a free slot.

Bodies on one account

  • Claude Code4 at once
  • Codex1 at a time
  • eitheras the machine says

Bodies on one model account share its sign-in, as several sessions of one person do, and each harness's own program renews it when it needs to. Loom has no renewer and no lock of its own. Claude Code takes a lock in the sign-in directory and reads the sign-in again before it renews; that was read in the program, in the version the core house pins, and has not been tested here with two bodies renewing at once. For Codex it is not established what happens then, so its bodies run one at a time on an account unless the machine's configuration says more. If a renewal is refused all the same, that body fails and its work is tried again. A job beyond the limit waits, and loom shows it as starting.

What is kept on the disk

  1. imagestwo a house, ten in all
  2. repositoriesthe eight used most recently
  3. leftoversunnamed images after a day, build cache after a week

After a build the worker removes what it no longer needs: house images beyond the two newest of each house and the ten newest in all, never one a job is using. A core house stays while a house image that is kept was built on it, which in practice is this week's and last week's. It keeps its copies of the eight repositories used most recently. It also asks the engine to remove unnamed images older than a day and build cache unused for a week, which reaches every such leftover on that engine, not only loom's.

When it goes wrong

What a person sees

A job fails, and the worker carries on

  • Build failed. The address is not https, the branch or Housefile is not there, the secret does not fetch the repository, the commit is past a limit, a step of the Housefile failed, or the core house could not be built (a download address that does not answer, say).

    worker build · exit code 22

  • The build ran out of time. The fetch, the core house's build when it was needed, and the house's build together took longer than the build's limit.

    worker build time · exit code 32

  • The house image does not meet the image contract, followed by what is at fault: loom.house, loom.house.harnesses or VOLUME.

    worker house · exit code 30

  • Launch failed. Node or the repository is not in the image at its place, or the engine could not start the container.

    worker launch · exit code 23

  • Runner failed. The machine has no sign-in directory for the job's account and harness.

    worker runner · exit code 27

  • Body config. The harness's body file is not in the image at its place, or is not a body file.

    body config · exit code 16

The worker stops when it starts, with one line

  • git 2.32.0 or later, which fetches each house's repository, could not be run on this machine.

    worker exit code 54

  • The directory the worker is installed in cannot give containers the body program. The worker's packages are not inside its own directory.

    worker exit code 55

  • A path the configuration gives to containers, or an engine socket, cannot be used. The line ends with the key of the entry at fault, never a path.

    worker exit code 52

  • The directory the worker is installed in has no definition of the core house. The install is not a whole one.

    worker exit code 56

  • The configuration has a key that a worker with container bodies no longer takes. A build command, a runner, directories listed for every agent at once, or a place in the container for a sign-in. The line ends with the key.

    worker exit code 53
Limits

What a machine needs, and what is not there

What a machine needs

  • A container engine that serves the Docker Engine API on a socket: Docker, or Podman.

    the engine

  • git 2.32 or later.

    to fetch

  • Network access from the engine's builds to Debian's mirrors, nodejs.org, Claude Code's release address and the npm registry: the core house is built from them, once a week.

    to build the core

  • The loom worker, installed with its packages inside its own directory, as npm install -g does. An install that shares packages with a project, the npx cache and pnpm are not supported.

    to run bodies

  • A token for the machine, and a configuration that names the engine's socket.

    Signing in

Not supported

  • A repository at an ssh address, or fetched with a deploy key.

    https only

  • Submodules. A submodule's files are not in the build.

    left out

  • Git LFS. A file kept in LFS reaches the build as the small pointer file the commit holds.

    pointer only

  • A base image in a registry that needs a sign-in, unless the engine itself is signed in to it. Loom passes no registry credential.

    the engine's own

Not built yet

  • The harness agy in the core house. There is no install of it pinned to a version and a checksum to put there; a house that wants it installs it in its own Housefile and lists it in the label.

    not in the core

  • A check, with real sign-ins, of two bodies on one account renewing at the same moment. Until it is done for Codex, its bodies run one at a time.

    to be run by a person

  • A conversation's harness session carried from one body to the next. Today each body starts its harness afresh.

    stated direction
