How a tile gets its data

One GraphQL endpoint, generated from the same schema as the database. A tile sends a query naming exactly the fields and connected things it wants, gets the rows, then receives changes as subscriptions over the websocket.

  • There is one definition of the data, and no hand-written reads.
  • A tile names exactly the fields and connected things it wants.
  • A page reads with one API call, backed by a fixed small number of SQL statements that does not grow with the number of rows, with visibility checked for whoever is asking.
  • After the first rows, loom sends only what changed.

How it works

One definition, one query, changes and the schema

One definition

schemageneratesendpoint

The endpoint is generated from the same Drizzle schema as the tables, so there is one definition of the data and no hand-written reads. GraphQL is a widely used standard with ready-made tools on both ends.

One query

  • Filter on real columns
  • Join the connected tables
  • Apply the caller's visibility
  • Sort

Loom handles the request in one API call using a fixed small number of sane SQL statements, independent of the number of rows. Several batched statements are fine. Filtering and visibility checks happen in the database.

Only changes

rowsthenchanges

After the first rows, changes arrive as subscriptions over the websocket. A tile never asks again for what it already has.

One schema

Defined onceDrizzle on SQLiteMoving to another database later is a configuration change.

The tables on every page of this site are one schema, defined once. A query is written against that schema, so nothing is stored as a bundle the database cannot look inside.

Who can see this

  • aChecked in the query. The visibility check runs inside the query, for whoever is asking. A caller never receives a row it may not see, or that row's changes.
  • bThe rule. A household owner sees everything, including what is private to another member. Anyone else sees what is in their projects, plus what belongs to agents they own. Private to a member means that member plus household owners.
  • cInstalled means trusted. The check is for callers from outside. Loom's own parts never ask each other for permission.

Data model

This page has no tables of its own. These are the things loom keeps that no screen reads.

  • machine_readsDiagnostic request metadata for the machine owner’s history. The answer text is never stored here.
  • migrationsThe list of changes already made to the database's shape, so each is applied once.
  • operation_resultsThe result of each recent write, kept 30 days, so a retry after a dropped connection returns the same answer and nothing happens twice.
  • notification_queueNotifications waiting to be sent to each device, and whether each arrived.
  • bridge_raw_eventsEvents exactly as Discord and Slack sent them, kept until they are turned into incoming messages: up to a day for one that cannot be read yet, and an hour from arrival once it has been. The one place loom stores something it does not look inside.
  • bridge_resumeWhere each Discord connection left off, so it can pick up after a restart, and the credential it was made under.
  • bridge_send_partsThe id the app gave each posted part of a reply, in order. A long reply goes out in parts; these say how far it got and which outside messages are the bot's own.
  • bridge_file_messagesWhich messages carried each kept Slack or Discord attachment. A file shared in two messages is listed under both and kept once.
  • bridge_send_filesThe files a post carries, kept only until the post is sent, dismissed or left in doubt.
  • terminal_credentialsThe machine and member an enrolled credential may report terminal sessions for.
  • terminal_sessionsThe private Comms thread and parent job for a harness session on a member’s machine.
  • terminal_runsThe parent job, run identifier and last transcript revision for each observed terminal run.
  • program_firingsProgram occurrences with the frozen assignment, period, execution job and reported outcome.
  • job_usageUsage counters for one job attempt. Missing counters stay unknown. The source identifies a report, transcript, program, or unknown counts.
  • conversation_sessionsA model program's own record of a conversation, sealed, kept between runs so the next one picks up where the last left off. One for a conversation and program; nothing but the next run reads it. It is erased when the household's keep time has passed since it was started, however often it was saved since; the next run then starts over.
  • secret_write_journalA two-step record between loom and the key holder so a value change interrupted by a crash is finished or undone, never half done.
